Moss / Inference evaluation
Work sample · 25 November 2026

Fast answers need clear evidence.

A small, practical evaluation of Moss’s portal, retrieval and task workflows—what worked, what needs clarity, and what remains untested.

Scope matters. These are live portal UI observations, not direct Inference or Tasks API results. The API harness and a terminal task failure remain untested. This is a review draft, not a benchmark.

What I observed

Retrieval · one question

A useful grounded answer

With Moss’s 55-document sample FAQ, Playground answered a password-reset question consistently with the sample fact. Without the index, it said the information was missing. Individual retrieved passages were not inspected.

Tasks · two runs

Structured result and fallback

An example.com task returned a title and paragraph that the portal marked schema-matching. A separate unreachable-site task reported the connection failure and succeeded at its instructed fallback; it was not a terminal job failure.

Validation · portal UI

Earlier feedback would help

Empty goals and malformed JSON were blocked. A JSON schema with an array root enabled Run but was rejected on submission. No raw HTTP status was captured.

Where I would focus

  1. Make total cost legible before a task runs

    Two tasks displayed $0.053 and $0.051 against $0.05 limits. The documented limit covers model calls, and other costs and in-flight work may exceed it; the display alone does not establish a billing defect.

  2. Explain latency and show the evidence

    For one request, Playground displayed 839 ms first token and 1,524 ms total; Logs & Traces displayed 78 ms and 595 ms. Explain measurement boundaries, and put retrieved passages beside grounded answers.

  3. Make integrations and failures easier to handle

    Validate schema constraints before enabling Run, and provide a streaming voice example with explicit no-results and task-failure handling.
